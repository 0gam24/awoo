# 네이버 빈틈 키워드 시스템 이식 프롬프트

다른 사이트 저장소의 Claude Code 세션에 아래 "프롬프트 본문"을 그대로 붙여 넣는다. 맨 위 [채울 것] 칸만 그 사이트에 맞게 바꾼다.

---

## 프롬프트 본문

```
[채울 것]
- 사이트: {도메인} · 사이트명 {이름} · 저장소 {경로}
- 이 사이트가 맡는 주제 축: {예: 부동산 — 청약·전월세·주택 세금}
- 주 독자: {예: 첫 집 마련을 준비하는 30대}
- 1차 출처(사실 확인 기준): {예: molit.go.kr, applyhome.co.kr, law.go.kr, nts.go.kr}
- 글 저장 형식: {예: src/data/posts/{date}/*.json 또는 MDX}
- 자동 발행 트랙: {있음/없음}

너는 이 사이트의 "네이버 빈틈 키워드 발굴 → 발행 지시" 시스템을 만든다.
참조 구현은 같은 PC의 awoo.or.kr 저장소(D:\Bibe-Code\00 Website\01 awoo)다.
그 코드는 읽기만 하고 구조를 가져온다. 키워드·트랙 정의·출처·함정은 반드시 이 사이트 특성으로 다시 설계한다.
awoo의 지원금 키워드나 분류표를 그대로 복사하면 실패다.

## 0. 목적과 원칙
- 목표는 하나다. 이 사이트 글이 네이버 통합검색 웹문서 블록 최상단에 올라가 트래픽을 모으고 애드센스 수익을 키우는 것.
- "검색량 큰 키워드"가 아니라 "자리가 열린 키워드"를 찾는다. 검색량은 정렬용이고, 발행 판단은 네이버 검색 결과 실측으로 한다.
- 검색량 없는 1위는 가치가 0이다. 이미 자사 글이 1~3위인 키워드는 새 글 대신 기존 글의 사실·날짜만 갱신한다.
- 네이버 어뷰징(매크로·계정 대량·링크 구매·클릭 조작)은 설계에서 제외한다.
- 자매 사이트 각도는 경쟁하지 않는다. 목록: D:\Bibe-Code\00 Website\01 awoo\docs\ops\sister-sites.json (roles).
- .env 파일은 읽지 않고 API 키 값을 출력하지 않는다.

## 1단계 — 사이트 프로파일 (코드 작성 전, 운영자 확인 필수)
저장소와 기존 글을 읽고 docs/ops/SITE-KEYWORD-PROFILE.md를 만든다. 운영자가 정해야 하는 것만 질문한다.
1. 주제 축 3~6개와 축별 "큰 키워드" 초안 → docs/ops/big-keywords.json
2. 트랙 3개를 이 사이트 버전으로 재정의
   - T1 물결 버스트: 짧은 기간에 검색 결과가 새로 열리는 "사건 × 분해 단위".
     awoo는 "지자체 × 지원금 공고·의회 가결", 창은 개시 D-7~D+8.
     이 사이트의 사건은 무엇이고, 분해 단위(지역 대신 단지·종목·모델·제도 등)는 무엇인가?
   - T2 대형 세부 롱테일: 큰 키워드의 세부 의도(조건·계산·기한·예외·비교·오류 해결).
   - T3 선점 캘린더: 해마다·달마다 돌아오는 날짜 이벤트 → docs/ops/landgrab-calendar.json
3. 패밀리(같은 대상에서 쓸 수 있는 글 종류). awoo는 A 정규본 / B 사후(사용처·미수령·대리) / V 검증형(부결·미확정·"없다" 확인).
   이 사이트의 A/B/V를 정의한다.
4. 사실 확인 필수 항목과 1차 출처 목록
5. 이 분야 함정 목록. 최소한 아래를 점검한다.
   - 상업 블로그가 만든 가짜 이름·가짜 차수("4차" 같은)
   - 연도가 섞인 옛 공문·보도자료가 검색 상위에 남아 있는 경우
   - 도구(계산기·조회 서비스)가 점령한 검색 결과 — 글로는 못 이긴다
   - 언론이 점령한 검색 결과
6. 자매 사이트 roles 기준 이 사이트 몫과 금지 각도
7. 발행 속도 규칙 초안: 일반 주제 하루 N건, T1은 창 안이면 상한 없음, 자동 발행은 별도 트랙

## 2단계 — 측정 도구 (awoo 참조 파일을 읽고 이 저장소에 새로 만든다)
- scripts/naver-rank-check.mjs 대응 — 검색 결과 정찰. `--mode=scout --query="..."`
  출력: rank(자사 순위), webDocCount, openSlots(상업·블로그·오래된 문서가 차지해 뺏을 수 있는 자리),
  mainGovAbove(관공서), pressAbove(언론), sisterAbove(자매), webDocOffset(통합검색 페이지에서 웹문서 블록이 시작하는 위치 %),
  above[](host·kind·title·stale), verdictT1/verdictT2(open|closed).
  호스트 분류표(관공서·언론·상업·자매·도구·자사)는 이 분야 기준으로 다시 만든다.
- scripts/keyword-radar.mjs 대응 — 네이버 API 신호 스냅샷(자동완성·연관검색·DataLab 추세·뉴스 모멘텀). 시드는 이 사이트 big-keywords.
- scripts/keyword-volume.mjs 대응 — DataLab 비율은 요청마다 정규화되므로 공통 기준어로 스케일한다.
  값이 0인 날짜는 채우고(alignToAxis), 최근 처음 나타난 키워드는 born으로 표시한다.
- 자사 순위 추적: docs/ops/rank-targets.json + 매일 측정 워크플로.
- 실유입(Search Advisor·GA) 주간 수치를 넣을 수 있으면 넣는다.

## 3단계 — 판정과 큐
- 잠금 장부(scripts/build-cluster-intents.mjs 대응 → docs/ops/cluster-intents.json)
  기존 글을 [분해 단위 × 패밀리]로 분류한다. 같은 조합의 새 글은 VETO, coreFacts 핵심값이 2개 이상 겹치면 FIX.
  명령: `--check "<대상>" <A|B|V> [--facts=파일]`, `--append <파일>`. 제목 단서로 패밀리를 판정하는 정규식은 이 분야 어휘로 만든다.
- 파이프라인(scripts/keyword-pipeline.mjs 대응)
  입력: 레이더·순위·검색량·big-keywords·캘린더·잠금 장부·기존 글
  → 후보 생성(T1/T2/T3/새 키워드/갱신)
  → 하루 검색 결과 실측 예산 안에서 측정(awoo는 35건 = T1 15·T2 5·새 키워드 10·재측정 5)
  → 노출 가능성 점수 → docs/ops/pipeline-queue.json + docs/ops/DAILY-KEYWORDS.md
- 노출 가능성 점수(exposureOf) 기본식. 가중치는 이 사이트 실측으로 조정한다.
  자리 열림 40
  + 빈자리(4개↑ 15 · 2~3개 10 · 1개 5)
  + 위에 관공서 없음 10(1곳 5)
  + 위에 언론 없음 10(3곳 이하 5)
  + 웹문서 블록 상단(offset 15% 미만 10 · 30% 미만 5)
  + 자사 4~10위 5 + 실유입(주 100↑ 10 · 30↑ 5) + 최근 7일 상승 5 + 신생 5 + 개시 창 안 5
  − 제도·사실 확인 필요 10
  자사 3위 이내는 후보에서 빼고 갱신으로 보낸다. 70↑ 높음, 45~69 중간.
  offset 30% 이상은 1위를 해도 사람 눈에 안 띄므로 닫힘으로 본다.
- 큐 상태: proposed / approved / published / hold / rejected.
  사람이 손으로 넣은 항목(id 접두 "빈틈:")은 자동 실행이 지우지 않게 21일 보존한다(awoo 2026-09-14 사고).
  글의 targetQuery가 큐 쿼리와 같으면 자동으로 published 처리한다.
- 갱신 후보: 기존 글 coreFacts 날짜가 D-3~D+1이면 "지난 기한·바뀐 날짜" 갱신을 제안한다.
  갱신 범위는 사실·날짜·updates[]·dateModified·표 행까지. 제목·slug·구조·전면 재작성은 금지.

## 4단계 — 운영자 화면과 명령
- "목록" 명령(.claude/commands/목록.md + scripts/ops-widget.mjs 대응)
  운영자가 "목록"이라고 치면 노출 가능성 순 10건을 채팅 위젯으로 띄운다.
  행마다: 쿼리 · 점수 · 이유 3개 · 조건 한 줄 · [발행 지시 ↗] [보류] 버튼, 미측정 항목은 [실측 ↗].
  위에 한 줄: "오늘 발행 N건(자동 N · 수동 N) · 어제 N건". git에 추적된 파일만 센다.
- 대시보드(/dashboard + scripts/ops-dashboard.mjs 대응): 로컬 HTML(gitignore), 앱 오른쪽 브라우저 패널에서 연다.
  킥포인트만: 오늘 할 일 / 어떤 키워드·어떻게 / 오늘 쓸 글감 / 순위 / 갱신 / 일정. 보기 복잡하면 실패다.
- /post 명령(.claude/commands/post.md 대응)
  인자에 "대시보드 지시"가 있으면 버튼을 누른 것이다. 큐 항목을 브리프로 쓰고 exposure.reasons를 작성자 브리프 맨 앞에 둔다.
  전략 단계와 결재 질문은 생략하고, 검증을 통과하면 발행한다. "보류:"로 시작하면 hold로 바꾸고 끝낸다.
- 에이전트(.claude/agents 참조, 이 분야로 다시 쓴다)
  emerging-keyword-hunter(새 빈틈 발굴, 정찰 25회 한도, 1차 출처로 실재 확인) · naver-serp-scout · post-writer ·
  fact-checker(1차 출처 교차검증, 점수 제안, "현재 문장 → 고칠 문장") ·
  publish-gatekeeper(자기잠식, 14자 shingle 15% 이하, 소멸성 부채, 미확정 단정, 스팸, 속도 VETO) · quality-gate

## 5단계 — 발행 규칙
- 순서: 작성 → 팩트체크·거부권 병렬 → FIX 반영 → lint → 커밋 → push → IndexNow → 큐 published → 잠금 장부 append.
- 발행 시기·수량은 운영자가 지시해도 Claude가 조절한다. 일반 주제는 하루 1건, 초과분은 검증 끝난 초안으로 두고
  "왜 오늘 안 내는지 · 언제 내는지"를 보고한다. T1은 창 안이면 상한 없음. 같은 날 제목 형태 3연속 금지.
- 품질 점수가 기준 미만이면 noindex되는 구조라면, 발행 전에 실제 검증 점수를 반드시 채운다. 0.0 방치와 점수 조작 둘 다 금지.
- 이미 자사가 상위인 자리에 새 글을 쓰지 않는다. 없는 제도·가짜 이름으로 글을 쓰지 않는다.
  수요가 크면 "없다·아직 아니다"를 1차 출처로 확인해 주는 V형으로 쓴다.
- 시한이 있는 글(행사·마감)은 종료 후 갱신 일정을 큐에 남긴다.

## 6단계 — 자동화
- GitHub Actions: 레이더 스냅샷(하루 2회), 순위 측정(매일), 파이프라인 보고(매일 오전 — 잠금 장부 재생성 후 실행, 결과 JSON 커밋).
- 봇이 쓰는 JSON은 포맷 검사(biome 등)에서 제외해 CI가 막히지 않게 한다.
- 매일 자동 발행이 있으면 수동 발행과 별도 트랙으로 센다.

## 완료 기준
1. 이 사이트 대표 키워드 3개로 정찰을 돌려 자사·관공서·언론·자매·상업·도구를 이 분야 기준으로 맞게 분류함을 보여준다.
2. 파이프라인 1회 실행으로 이 사이트 주제의 후보 5건 이상이 노출 가능성 순으로 큐와 보고서에 나오고, 후보마다 이유·조건이 붙는다.
   awoo 주제 키워드가 섞이면 실패.
3. "목록" → 위젯 → [발행 지시] → /post 흐름이 초안 1건의 검증까지 끝까지 동작한다.
4. 잠금 장부가 기존 글을 분해 단위 × 패밀리로 분류하고, 중복 후보를 VETO한다.
5. docs/ops/KEYWORD-PLAN-{날짜}.md에 트랙·점수식·실측 예산·함정·운영자 결정 표가 있다.
```

## 사이트별 T1 "사건 × 분해 단위" 예시 (1단계 질문의 출발점)
